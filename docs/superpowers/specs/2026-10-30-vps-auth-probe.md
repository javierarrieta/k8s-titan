# T0a — VPS auth probe: what is actually protected

Measured 2026-10-30. Read-only. This is the falsification test for spec §3, which was written as a
hypothesis with three live alternatives and explicitly said a DB export could not settle it.

**It settles it.** The VPS's per-app auth is authentik's embedded reverse-proxy outpost, enforcing at
the router for nine hosts, and six further hosts are open to the internet with no auth of any kind.

## Method

Unauthenticated `curl` from this workspace, no cookies, no redirect following on the primary pass:

```sh
curl -s -m 20 -o /dev/null -D <hdrfile> \
  -w "%{http_code}|%{num_redirects}|%{remote_ip}|%{ssl_verify_result}" "https://<host>/"
```

Host list taken from the live cluster (`kubectl --context vps get ingress -A -o json`), not from git —
ten `Ingress` objects, twenty-two distinct hostnames resolving to the VPS address. A follow-up pass re-probed
deep paths (`/api/health`, `/api/v1/query`, `/graph`) to test whether any gate applies only to `/`.

## What this proves

**1. Hypothesis 2 of spec §3 holds; hypothesis 1 is dead; hypothesis 3 was never in play.**
The nine class-A hosts are gated by authentik's embedded outpost, whose Ingress
(`auth/ak-outpost-reverse-proxy-outpost`) is generated by authentik from UI-created state and lists all
nine hosts. Protection is therefore enforced without ever touching the application's own Ingress — which
is exactly why git shows nothing and why §3 could not call this from the tree alone. Hypothesis 3
(network-layer gating) explains nothing observed: every host above is reachable from the public
internet, and the class-D hosts answer 200 to anyone.

**2. The gate is router-level, not path-level — it is not bypassable by deep-linking.**
Every class-A host was re-probed at a deep path (`/api/health`, `/api/v1/query?query=up`, `/graph`,
`/api/status`) and every one returned 302, not 200. Following the redirect chain lands on
`https://auth.v.arrieta.eu/if/flow/default-authentication-flow/`, never on the application.

**3. Each gated host has its own authentik Application and its own OAuth2 `client_id`.**
Observed distinct client IDs include `s3fdpIYFeXfzJTNzzT1bSRuWcwRZ7OZaaTqJKCll` (q1),
`vNImYdJYDplBstC1PPZhC355QiaB7MIdG4odmNBA` (bentopdf) and `0OdqvWFXblnJ0alLgT4BBnsh2TfwPxRtTOIyfC4E`
(tesla). Requested scope is `profile entitlements ak_proxy email openid` on all three. This is the
strongest available evidence for what T0 must export: **per-application**, not per-outpost. A single
outpost object is not the unit of migration; the Application is.

*Note on the client IDs above:* an OAuth2 `client_id` is a public identifier, not a secret — it appears
in every unauthenticated redirect this cluster issues. The `client_secret` was not observed and is not
recorded here, per T0's credential-exclusion rule.

**4. Six hosts are open, and four of them are in the migration's scope.**
`chiclana-hass`, `databasus`, `openwebui` and `tr` (trading-reports) answer 200 to an unauthenticated
request. The kanghuru pair is expected — it is a public product. **Putting the first four behind
authentik on titan is a behaviour change, not a parity move**, and it can break clients that authenticate
some other way or not at all: a Home Assistant mobile app, a `databasus` cron hitting its own API, a
script scraping `tr`. Each of those four needs an explicit keep-open-or-gate decision in its ticket
(#112, #113, #106) rather than inheriting the epic's forwardAuth default.

**5. Grafana is not authentik-gated on the VPS.**
It 302s to its own `/login`. The login page does reference OAuth/SSO, so an SSO option is configured,
but the native login page is the landing surface and `GF_AUTH_GENERIC_OAUTH_*` is commented out in git
(spec §3.1). Titan's grafana is behind `observability-grafana-auth` forwardAuth. So the migration
*changes* grafana's auth model rather than reproducing it — which is fine, and is what §3.1 already
concluded, but it is now measured rather than inferred.

**6. `hass.v.arrieta.eu` is not serving anything.**
400 for `/`, `/api/`, and with a browser User-Agent; `http://` 301s to `https://` and then 400s the same
way. The response comes from the application's own `aiohttp` server, so the request reaches Home
Assistant and the application rejects it. A plausible cause is a reverse-proxy header mismatch (HA
rejecting an untrusted `X-Forwarded-For`/`X-Forwarded-Proto` or `Host`), but **that is a candidate, not
a finding** — it was not tested. `chiclana-hass` on the same cluster returns 200, so this is specific to
this instance. #112 covers both; whoever picks it up should establish whether the instance is healthy
before migrating it, because there is currently no way to verify a migrated HA works when the source
does not answer.

**7. The Traefik dashboard is published publicly** at `traefik.v.arrieta.eu`, behind a 401 challenge.
Not authentik-gated. Out of migration scope but worth knowing; titan's own dashboard/API are off.

## What this does not answer

- **`access_group` per Application is still unknown.** This probe proves a host is gated; it cannot say
  whether the gate is "any authenticated account" or a specific group. That is T0's contract and it is
  the column spec §9 flags as the one that decides whether a host is gated open to everyone.
- **Group membership and identity parity are unmeasured.** Still T0's exit criterion (spec §3.3).
- **The declared-vs-actual middleware comparison is incomplete.** `k8s-reader` is **Forbidden** from
  listing `middlewares.traefik.io` on the VPS (`auth can-i` returns `no`), and `ingressclasses` likewise.
  An initial read of an empty result set here nearly produced the false conclusion "the VPS has no
  Middleware objects"; it has some, they are simply not readable with this identity. Anything in T0 that
  needs the VPS middleware set requires an admin context.
- **Single-GET sampling.** One request at `/` plus a handful of deep paths. A host could gate `/api/*`
  and leave another prefix open; this probe would miss that.
- **No authenticated testing.** Nothing here proves the gates *admit* the right people, only that they
  refuse the wrong ones.
